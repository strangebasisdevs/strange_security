# Organization security baseline

This is the public catalogue of security controls that every repository in the
`strangebasisdevs` organization is held to, public and private alike. The
reusable workflows in this repository (strange_security) are the enforcement for
the scan controls, and this repository is the home of the policy. Public
defaults, such as the organization `SECURITY.md`, live in
`strangebasisdevs/.github`.

The catalogue is generic on purpose. It states each control, why it exists, how
it is set up on GitHub, what the same control is on another forge, and how it is
checked. It does not list repositories, exceptions, counts or setting values.
Those live in a private governance repository that holds the inventory, the
per-repository status generated by an audit, the dated exceptions, the
organization settings record, the ruleset definitions and the apply and audit
tooling.

## Principles

- **The restrictive option wins, and its cost is written down.** When two
  settings are possible, the stricter one is used, and what it costs (a slower
  merge, a lost feature) is recorded next to the decision.
- **Everything is pinned.** Actions, reusable workflows and images are
  referenced by an immutable identifier, never by a mutable name.
- **Least privilege.** Tokens, workflows and people get the smallest access that
  does the job.
- **Pull requests only, signed, on every default branch.** Nothing reaches a
  default branch without a reviewed pull request and a verified signature.
- **Every scan is a required check.** A scan that can be ignored is not a
  control.
- **Decisions are recorded with absolute dates.** An exception or a setting
  decision carries the calendar date it was made, never "last month".

Every control below has the same fields: the control ID (the OpenSSF Scorecard
check name where one exists, otherwise an `ORG-nn` ID), a vendor-neutral
statement, the rationale, the GitHub implementation, the portable equivalent on
another forge such as Forgejo or GitLab, and how it is verified.

## Controls

### Default-branch integrity

- **Control ID:** Branch-Protection
- **Statement:** The default branch cannot be deleted, cannot be force-pushed,
  keeps a linear history, accepts only commits with a verified signature, and
  has no bypass actor for these rules.
- **Rationale:** History is the audit trail and the supply-chain root. A
  rewritten or unsigned history cannot be trusted, and a bypass list is a
  standing weakness.
- **GitHub implementation:** A repository or organization ruleset targeting the
  default branch with the rules that restrict deletions, block force pushes,
  require linear history and require signed commits. The bypass list for these
  rules is empty.
- **Portable equivalent:** A protected branch with force-push and deletion
  disabled, a fast-forward or squash-only merge method, and a push rule that
  rejects unsigned commits (Forgejo and GitLab both offer these).
- **Verification:** The audit reads the active rulesets of each repository and
  compares them with the stored definition. A missing rule or a non-empty bypass
  list is a finding.

### Pull-request gate

- **Control ID:** Code-Review
- **Statement:** Changes reach the default branch only through a pull request
  with an approving review from a code owner. A new push dismisses earlier
  approvals, the most recent push must be approved by someone other than its
  author, and every review thread must be resolved before merging. Only squash
  merging is allowed. The single bypass is an organization administrator in
  pull-request mode, exercised per pull request by a human and audited.
- **Rationale:** A second pair of eyes on every change, on the code that will
  actually merge, is the main defence against a mistake or a compromised
  account. Squash keeps one signed, reviewed unit per change.
- **GitHub implementation:** The pull-request rule of the same ruleset: pull
  request required, code owner review required, stale approvals dismissed on
  push, approval of the most recent push required, conversation resolution
  required, and squash as the only allowed merge method. The bypass actor is the
  organization administrator role, set to the pull-request bypass mode, so it
  can only be used from a pull request and appears in the audit log.
- **Portable equivalent:** Protected-branch approval rules with code owner
  approval, approvals reset by new commits, an author-cannot-approve setting, an
  all-threads-resolved merge condition and a squash-only merge method.
- **Verification:** The audit compares the pull-request rule parameters and the
  bypass actors with the stored definition. Use of the bypass is reviewed from
  the audit log.

### Scan gate

- **Control ID:** ORG-01
- **Statement:** The Semgrep static analysis, Trivy filesystem scan and Gitleaks
  history scan reusable workflows of strange_security are required status checks
  on the default branch. The checks are strict, so a branch must be up to date
  before merging, and they have no bypass. A repository joins the gate once its
  gate workflow has run green on its default branch; before that, the required
  check would block its own first pull request.
- **Rationale:** Static analysis, dependency and secret scanning run the same way
  everywhere, are maintained in one place and cannot be switched off by the
  repository they scan.
- **GitHub implementation:** The thin caller workflow described under "Thin
  caller workflow" runs the three reusable workflows. An organization ruleset
  requires their status checks, named `Semgrep / Semgrep scan`,
  `Trivy / Trivy filesystem scan` and `Gitleaks / Gitleaks history scan`, with
  the strict option and an empty bypass list. The ruleset applies to the
  repositories that carry a custom property marking them as joined to the gate,
  which is set once the gate has run green on the default branch.
- **Portable equivalent:** The same three scanners (Semgrep, Trivy, Gitleaks) run
  in the forge's CI, for example as Forgejo Actions or GitLab CI jobs included
  from a central project, and their job names are required status checks on the
  protected branch with "branch must be up to date" enabled.
- **Verification:** The audit checks that the ruleset requires the three checks,
  that the custom property is set on every repository whose gate is green, and
  that the gate workflow is present. A repository with a green gate that has not
  joined is a finding.

### Repository-specific required checks

- **Control ID:** ORG-02
- **Statement:** Checks that only make sense for one repository, such as its test
  suite, linters or build, are also required status checks on its default branch.
- **Rationale:** The shared gate covers security, not correctness. A check that is
  not required is advisory and is eventually ignored.
- **GitHub implementation:** A repository ruleset, added alongside the
  organization one, requiring the repository's own check names.
- **Portable equivalent:** Additional required status checks on the protected
  branch.
- **Verification:** The audit lists the required checks per repository, and a
  workflow whose check is not required is reported.

### Thin caller workflow

- **Control ID:** Pinned-Dependencies
- **Statement:** A repository's security gate workflow only calls the shared
  reusable workflows. Each call is pinned by full commit SHA with a release
  comment, and Dependabot moves the pin. Every other action or reusable workflow
  the repository uses is pinned the same way. Nothing references a branch, a tag
  or a short SHA.
- **Rationale:** A tag or branch can be moved to malicious code after review. A
  full commit SHA cannot. A thin caller keeps the logic in one reviewed place.
- **GitHub implementation:** `uses: owner/repo/.github/workflows/file.yml@<full
  commit SHA> # vX.Y.Z`. The template is `baseline/templates/security_gate.yml`.
  The organization setting that requires actions to be pinned to a full SHA makes
  GitHub itself refuse mutable references. Dependabot version updates for the
  `github-actions` ecosystem propose each new pin, and its pull request is
  reviewed like any other.
- **Portable equivalent:** Include or reference shared pipelines by commit hash
  (a GitLab `include: project` with `ref` set to a commit; a Forgejo action
  reference by commit SHA), and keep a dependency bot opening the update.
- **Verification:** A test in strange_security checks that its own workflows and
  the consumer template are pinned. The audit checks consumers for mutable
  references and for a pin that is stale compared with the current release.

### Workflow permissions and credentials

- **Control ID:** Token-Permissions
- **Statement:** Every workflow declares explicit top-level `permissions`, with
  read access unless a job needs more, and then only for that job. Checkouts do
  not persist the token in the local git configuration.
- **Rationale:** A compromised step can only use what the token holds. A token
  left in the git configuration is available to every later step and to anything
  written into the workspace.
- **GitHub implementation:** A top-level `permissions:` block in each workflow
  and `persist-credentials: false` on each `actions/checkout`. The organization
  default for the workflow token is read-only.
- **Portable equivalent:** Scope the CI job token to the minimum (a GitLab job
  token allowlist, Forgejo token permissions) and avoid leaving credentials in
  the checkout.
- **Verification:** A workflow linter and the Scorecard check read the
  permissions. The audit reports a workflow with no top-level block or a
  checkout without `persist-credentials: false`.

### Dangerous workflow patterns

- **Control ID:** Dangerous-Workflow
- **Statement:** No workflow uses the `pull_request_target` trigger to run code
  from a pull request, and no `workflow_run` workflow has access to secrets or a
  write token while handling the output of an untrusted run. Untrusted input such
  as titles, branch names and comments is never interpolated into a script.
- **Rationale:** These patterns run attacker-controlled code with the base
  repository's secrets and are the commonest route to a stolen token.
- **GitHub implementation:** Plain `pull_request` workflows with read-only
  tokens; values reach scripts through environment variables, not inline
  expressions. Fork pull requests also need approval (see "Fork pull requests").
- **Portable equivalent:** Do not expose protected variables to pipelines
  triggered from forks or from untrusted branches.
- **Verification:** The Scorecard Dangerous-Workflow check and a workflow linter,
  plus the audit's search for the two triggers.

### Dependabot version updates

- **Control ID:** Dependency-Update-Tool
- **Statement:** A dependency update bot is configured for every package
  ecosystem present in the repository, on a regular schedule, with a limit on
  open pull requests and a cooldown before it adopts a newly published release.
- **Rationale:** Updates are small and frequent instead of large and late. The
  cooldown gives the community time to find and yank a compromised release before
  it is adopted.
- **GitHub implementation:** `.github/dependabot.yml` with one entry per
  ecosystem, the same weekly schedule and a cooldown. The template is
  `baseline/templates/dependabot.yml`. An excluded directory or dependency is an
  exception.
- **Portable equivalent:** Renovate, which runs against Forgejo and GitLab, with
  an equivalent minimum release age and schedule.
- **Verification:** The audit compares the ecosystems found in the repository with
  the entries of the configuration and checks the cooldown. A missing ecosystem
  is a finding.

### Dependency alerts and security updates

- **Control ID:** Vulnerabilities
- **Statement:** The dependency graph, vulnerability alerts and automated
  security updates are enabled, and the repository has no known unresolved
  vulnerability in its dependencies.
- **Rationale:** The alert is the notification that a dependency already in use
  has become unsafe, independent of the version update schedule.
- **GitHub implementation:** Dependency graph, Dependabot alerts and Dependabot
  security updates enabled through the organization's default security
  configuration for new repositories, and applied to existing ones.
- **Portable equivalent:** The forge's dependency scanning feature, or a
  scheduled scanner run against an advisory database.
- **Verification:** The audit reads the three settings per repository. Open alerts
  are reported, and the gate's Trivy scan fails a pull request on a fixable high
  or critical vulnerability.

### Secret scanning and push protection

- **Control ID:** ORG-03
- **Statement:** Secret scanning and push protection are enabled where the
  platform offers them. Repositories without push protection rely on the gate's
  secret scans, which fail the pull request on a finding.
- **Rationale:** A secret that never reaches the remote needs no rotation.
  Detecting it afterwards is the second line.
- **GitHub implementation:** Secret scanning and push protection from the default
  security configuration, where the plan includes them. The Gitleaks history scan
  and the Trivy secret check in the gate cover the rest.
- **Portable equivalent:** A server-side pre-receive secret check (GitLab secret
  push protection) plus the same scanners in CI.
- **Verification:** The audit reads both settings per repository and notes which
  repositories depend on the gate alone. A secret finding means the credential is
  exposed: rotate it first.

### Private vulnerability reporting

- **Control ID:** ORG-04
- **Statement:** Public repositories offer a private channel for reporting a
  vulnerability, so a report never has to be a public issue.
- **Rationale:** A public report of an unfixed flaw is a disclosure.
- **GitHub implementation:** Private vulnerability reporting enabled on each
  public repository, which shows the "Report a vulnerability" button in its
  Security tab.
- **Portable equivalent:** Confidential issues, or a security contact address in
  the security policy.
- **Verification:** The audit reads the setting for every public repository.

### Code scanning

- **Control ID:** SAST
- **Statement:** Public repositories run static analysis that reports to the code
  scanning dashboard: the gate uploads its SARIF reports and CodeQL runs in
  default setup. Repositories without code scanning rely on the gate's checks
  failing the pull request.
- **Rationale:** Findings stay visible after a pull request merges, and a second
  analysis engine finds different problems.
- **GitHub implementation:** SARIF upload from the Semgrep and Trivy gate
  workflows, and CodeQL default setup on public repositories. A private
  repository without code scanning sets `upload-sarif: false` in its gate and
  keeps the checks.
- **Portable equivalent:** The forge's SAST report or security dashboard, fed with
  the same SARIF files.
- **Verification:** The audit reads the code scanning default setup state and
  whether alerts exist. A failed upload is visible in the gate's job.

### Security policy

- **Control ID:** Security-Policy
- **Statement:** A published security policy tells people how to report a
  vulnerability. Public repositories inherit the organization default unless
  their scope differs.
- **Rationale:** A reporter needs one obvious, private route and an idea of what
  to expect.
- **GitHub implementation:** `SECURITY.md` in `strangebasisdevs/.github` is the
  default for public repositories without their own. A repository whose scope
  differs adds its own from `baseline/templates/SECURITY.md`. Private
  repositories need none.
- **Portable equivalent:** A `SECURITY.md` or security contact page at project
  level.
- **Verification:** The Scorecard Security-Policy check, and the audit confirms
  that every public repository has its own file or inherits the default.

### Code owners

- **Control ID:** ORG-05
- **Statement:** A code owners file defines who "a code owner review" means. It
  starts with a default owner for every path and adds the files that hide or
  permit findings, such as exception and allowlist files, with their reviewer.
- **Rationale:** The pull-request gate is only as meaningful as the list of who
  may approve. Paths that can weaken the scans need an owner by name.
- **GitHub implementation:** `.github/CODEOWNERS`, from
  `baseline/templates/CODEOWNERS`. The file itself is covered by the default
  rule.
- **Portable equivalent:** A `CODEOWNERS` file (GitLab, Forgejo) with approval by
  code owner enforced on the protected branch.
- **Verification:** The audit checks that the file exists, starts with the default
  rule and parses without error.

### Merge settings

- **Control ID:** ORG-06
- **Statement:** Only squash merging is allowed, head branches are deleted after
  merging, auto-merge is off, and the interface suggests updating a branch that
  is behind.
- **Rationale:** One reviewed, signed unit per change, no stale branches, and no
  merge that happens without a human at the moment of merging.
- **GitHub implementation:** Repository merge settings for the merge methods,
  automatic head branch deletion, the auto-merge switch and the suggestion to
  update the branch.
- **Portable equivalent:** The project merge method, source branch deletion and
  merge-when-green settings.
- **Verification:** The audit reads these repository settings and reports any that
  differ.

### Fork pull requests

- **Control ID:** ORG-07
- **Statement:** Workflows from fork pull requests need approval before they run,
  for all outside collaborators.
- **Rationale:** A fork pull request can change the workflow it is about to run.
  A human looks first.
- **GitHub implementation:** The repository and organization setting that
  requires approval for workflow runs from fork pull requests, set to the
  strictest option (all outside collaborators).
- **Portable equivalent:** Restrict pipelines from forks to manual or approved
  runs (GitLab pipelines for merge requests from forks, Forgejo approval for
  first-time contributors).
- **Verification:** The audit reads the setting for each repository and for the
  organization.

### Agents policy

- **Control ID:** ORG-08
- **Statement:** Dependency bots, coding agents and review agents may open pull
  requests and comment on them. None may approve a pull request, merge one, or
  push to a default branch.
- **Rationale:** An automated author needs a human reviewer, and an automated
  reviewer does not replace one. Approval and merge are the human decisions the
  gate relies on.
- **GitHub implementation:** The ruleset has no bypass actor for an agent, and
  code owners are people or teams, never apps. Agent accounts and apps get write
  access to branches and pull requests only, never to a default branch or to the
  rulesets. Auto-merge is off, so nobody can queue a merge on their behalf.
- **Portable equivalent:** The same on any forge: bot accounts are not code
  owners, not approvers, and not allowed to push to the protected branch.
- **Verification:** The audit lists the apps and bot accounts with access, checks
  the approvals on merged pull requests for a bot approver, and reports any
  default-branch commit that did not come from a merged pull request.

### Organization settings

- **Control ID:** ORG-09
- **Statement:** Only owners create repositories. New repositories get the default
  security configurations. Artifact and log retention is shortened from the
  platform default. Actions must be pinned to a full commit SHA. The default
  workflow token is read-only, and only an allowlist of actions may run.
- **Rationale:** Settings at organization level cover repositories that nobody
  has configured yet, and shorter retention reduces what an attacker can read
  from old artifacts and logs.
- **GitHub implementation:** Organization settings for repository creation,
  default security configurations, Actions retention, the SHA pinning
  requirement, the default workflow permissions and the allowed actions policy.
  The values are kept in the private organization settings record.
- **Portable equivalent:** Instance or group settings for the same things: who can
  create projects, default security features, artifact expiry, default CI token
  scope and an allowlist of shared pipelines.
- **Verification:** The audit reads the organization settings and compares them
  with the record. Drift is a finding.

### Exceptions process

- **Control ID:** ORG-10
- **Statement:** A deviation from this catalogue is recorded as an exception with
  the date it was approved, a reason and the compensating control, in the private
  governance repository. Exceptions are reviewed whenever the audit runs, and an
  exception is removed when its reason ends.
- **Rationale:** A control that is quietly skipped is no control. A recorded
  exception shows what is accepted, why, and what covers the gap.
- **GitHub implementation:** A dated entry in the private ledger, approved in a
  pull request by a code owner. No exception is kept in a public file.
- **Portable equivalent:** A tracked, dated decision record in any private
  repository or issue tracker, with review.
- **Verification:** The audit lists exceptions with their dates and checks that
  each deviation has one. A deviation without an entry, or an entry whose
  compensating control is gone, is a finding.

### Verification and drift

- **Control ID:** ORG-11
- **Statement:** A read-only audit regenerates the status of every repository
  against this catalogue. A difference between the recorded and the actual state
  is a finding.
- **Rationale:** Settings drift. Unless somebody compares, the catalogue describes
  an intention, not a state.
- **GitHub implementation:** Tooling in the private governance repository reads
  repository, ruleset and organization settings through the API with a read-only
  credential and regenerates a status page. The page is not published.
- **Portable equivalent:** The same script against another forge's API, or the
  forge's compliance dashboard.
- **Verification:** The audit is the verification. Running it, and acting on its
  findings, is part of every review of the baseline.

## Consumer files

A repository joining the baseline copies the files in
[`baseline/templates/`](../baseline/templates/):

- `baseline/templates/security_gate.yml`, the thin caller workflow;
- `baseline/templates/dependabot.yml`, the version update configuration;
- `baseline/templates/SECURITY.md`, the public security policy, for repositories
  whose scope differs from the organization default;
- `baseline/templates/CODEOWNERS`, the default code owner rule.

Each file starts with a comment saying what the consumer must change. The
templates sit outside `.github/workflows/`, so the checks of the reusable
workflows never read them.

Changes to this document go through a pull request reviewed like any other
security change.
